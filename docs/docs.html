CODEFORGE Docs

Full reference for the CODEFORGE multi-agent code generation system. Built on LangGraph, powered by Groq Llama 3.3 70B, with Tavily web search, LangSmith observability, and a Flowise visual canvas.

✅ 20/20 Tests Passing

All tests pass on Python 3.10+. Run python3 tests/test_suite.py to verify your setup.

How it works in one sentence

You give CODEFORGE a coding task in plain English. Six specialized agents pass it through a state machine: Orchestrator → Planner → Coder (with web search) → Reviewer (loops back if quality < 7) → Executor → Debugger (loops back if runtime fails). You get working, reviewed, executed code.

Configuration

All configuration is via a .env file in the project root. Copy .env.example to get started. The file is gitignored and never committed.

⚠️ LangSmith key type matters

Use a personal token (lsv2_pt_*), not a service key (lsv2_sk_*). Service keys may have null workspace IDs and will return 403 on run creation.

Agents

Six agents run in sequence. Each reads the full AgentState and writes only the fields it owns. Feedback loops are handled by LangGraph conditional edges.

1. Orchestrator

01 ORCHESTRATOR agents/orchestrator.py

Reads the raw user task and normalizes it. Calls Groq with a strict JSON-response prompt. Detects the programming language (defaults to Python if ambiguous) and produces a clean task summary for all downstream agents.

Reads from state
task (raw)
Writes to state
task (summarized)language

Output format

// JSON response from Groq
{
  "task_summary": "Implement a BST with insert, search, delete",
  "language": "python"
}

2. Planner

02 PLANNER agents/planner.py

Turns the task summary into a numbered step-by-step implementation blueprint. Identifies required functions, classes, libraries, edge cases, and error handling requirements.

Reads from state
tasklanguage
Writes to state
plan

3. Coder

03 CODER agents/coder.py

Writes complete, production-quality code following the plan. Uses llm.bind_tools([search_tool]) to optionally call Tavily web search (up to 3 times per iteration) when it needs current documentation. Context-aware: reads review_feedback and debug_notes to fix prior attempts.

Reads from state
tasklanguageplanreview_feedbackdebug_notes
Writes to state
codecode_iteration

Tools available

TavilySearch — real-time web search. Triggered automatically when the coder needs to look up an API, library method, or implementation pattern. Max 3 calls per coding iteration.

Code extraction

Code is extracted from the LLM's response using regex to find fenced code blocks (```python ... ```). If no fence is found, the full response is used as-is.

4. Reviewer

04 REVIEWER agents/reviewer.py

Scores code on five criteria and decides whether to approve or send back to the Coder. The routing logic in graph/workflow.py reads review_approved and either advances to Executor or loops back to Coder.

Reads from state
tasklanguagecodecode_iteration
Writes to state
review_approvedreview_feedback

Scoring criteria

#CriterionWhat it checks
1CorrectnessDoes it actually solve the task?
2CompletenessIs it runnable right now without modifications?
3Code QualityIs it clean and idiomatic for the language?
4Error HandlingAre edge cases and invalid inputs handled?
5SecurityNo obvious vulnerabilities (injection, unsafe eval, etc.)?

Approval rule: score ≥ 7 AND no critical issues → approved: true. Below threshold → returns to Coder with specific feedback. After MAX_CODE_ITERATIONS rounds, forces approval regardless of score.

JSON response format

{
  "approved": true,
  "score": 9,
  "issues": [],
  "summary": "Clean BST implementation, all edge cases handled"
}

5. Executor

05 EXECUTOR agents/executor.py

Runs the approved code in an isolated subprocess. Writes code to a temp file, executes with sys.executable, and captures stdout/stderr.

Reads from state
codelanguage
Writes to state
execution_outputexecution_successfinal_code

Language handling

LanguageAction
PythonWrite to /tmp/*.py, run via subprocess.run([sys.executable, tmp])
JavaScript / TypeScriptMarks execution_success=True with note — no runtime available
Java / Go / Rust / otherSame — marks success, skips execution

The 30-second timeout is a hard kill via subprocess.run(..., timeout=30). Timeouts are caught and returned as an error to the Debugger.

6. Debugger

06 DEBUGGER agents/debugger.py

Receives the failed code and full error traceback. Diagnoses the root cause (not just the symptom) and returns a complete fixed version. Increments debug_attempts — when it reaches MAX_DEBUG_ATTEMPTS, the workflow ends.

Reads from state
tasklanguagecodeexecution_outputdebug_attempts
Writes to state
code (fixed)debug_notesdebug_attempts

Response format

DIAGNOSIS: IndentationError on line 14 — mixed tabs and spaces

```python
# complete fixed code here
```

Shared State

All agents communicate through a single AgentState TypedDict defined in state/schema.py. LangGraph passes this state through the graph — each agent receives the full object and returns only the fields it modifies.

class AgentState(TypedDict):
    task: str                    # raw task → summarized by Orchestrator
    plan: str                    # implementation plan from Planner
    language: str                # detected language (e.g. "python")
    code: str                    # current code from Coder/Debugger
    code_iteration: int          # how many times Coder has run
    review_feedback: str         # Reviewer's rejection reason
    review_approved: bool        # True = proceed to Executor
    execution_output: str        # stdout/stderr from subprocess
    execution_success: bool      # True = code ran without error
    debug_attempts: int          # how many Debugger cycles ran
    debug_notes: str             # Debugger's diagnosis
    current_agent: str           # name of the currently active agent
    agent_log: List[str]         # chronological activity log
    final_code: str              # confirmed working code (set by Executor)
    final_explanation: str       # human-readable explanation
    messages: Annotated[List, add_messages]  # LangChain message history

Routing Logic

Two conditional edges drive the feedback loops in graph/workflow.py:

After Reviewer

def _route_after_review(state: AgentState) -> str:
    if state["review_approved"] or state["code_iteration"] >= MAX_CODE_ITERATIONS:
        return "executor"    # approved, or max loops hit
    return "coder"            # send back for rework

After Executor

def _route_after_execution(state: AgentState) -> str:
    if state["execution_success"] or state["debug_attempts"] >= MAX_DEBUG_ATTEMPTS:
        return END             # success, or max debug attempts
    return "debugger"         # execution failed — debug it

LangSmith Integration

LangSmith traces every LLM call in the pipeline automatically when enabled. No code changes required — tracing is controlled entirely by environment variables.

Enable tracing

# In .env
LANGSMITH_API_KEY=lsv2_pt_...    # personal token, not service key
LANGSMITH_TRACING=true
LANGSMITH_PROJECT=CODEFORGE

What gets traced

  • Every agent's LLM call (prompt + response)
  • Token counts (input / output / total)
  • Latency per call
  • Tool calls (Tavily search queries + results)
  • Run metadata (agent name, iteration count)
View at smith.langchain.com

Open smith.langchain.com → Projects → CODEFORGE. Each full pipeline run appears as a top-level trace with nested agent spans.

Flowise Integration

CODEFORGE ships with a script that automatically creates and deploys a visual agent canvas in Flowise Cloud.

Deploy

# Set FLOWISE_API_KEY in .env, then:
python3 flowise/create_flow.py

The script creates a CHATFLOW with three nodes — ChatGroq → BufferMemory → CODEFORGE Agent — with real edge connections and the Groq API key pre-embedded. It prints the canvas URL when done.

Canvas structure

NodeTypeRole
ChatGroqChat ModelLlama 3.3 70B via Groq
BufferMemoryMemoryConversation history
CODEFORGE AgentTool Agent5-step code generation with system prompt
Flowise Cloud credential API is restricted

Flowise Cloud returns 403 when creating credentials via API. The script embeds the Groq key directly in the node's inputs dict as a workaround. This is fine for personal use — for production, add the credential via the Flowise UI.

FAQ

Which Groq models can I use?

Any model supported by Groq and accessible via langchain-groq. The default is llama-3.3-70b-versatile. Change it with MODEL_NAME in .env. Other tested options: llama3-8b-8192 (faster, lower quality), mixtral-8x7b-32768.

Why subprocess for code execution instead of exec() or PythonREPL?

Subprocess runs in a completely separate Python process, so a crash, infinite loop, or malicious code cannot affect the main CODEFORGE process. exec() shares the same process memory and namespace. PythonREPLTool from LangChain is a thin wrapper around exec().

Does it work with non-Python languages?

Yes — Orchestrator detects the language and Coder writes idiomatic code for it. Execution is Python-only (subprocess). JavaScript, TypeScript, Go, Rust, Java, C++, and others get full generation + review, then execution_success is set to True with a note that execution was skipped.

What happens if Groq rate-limits me?

The ChatGroq instance is configured with max_retries=3 and automatic exponential backoff. Heavy consecutive pipeline runs (5+ in a row) can exhaust the free 12,000 TPM limit. Wait 60 seconds and retry.

Can I use a different LLM provider?

Yes. Change config/llm.py to return any BaseChatModel-compatible object (ChatOpenAI, ChatAnthropic, ChatGoogleGenerativeAI, etc.). All agents use the model via the same interface.
